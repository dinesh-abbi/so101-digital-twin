## Stage 2 — Scan the servos (~5 min, read-only, nothing moves)

```powershell
D:\robotics\so101-vr\.venv\Scripts\python.exe D:\robotics\so101-vr\scan_motors.py COM8
```

This issues only PING and READ. It cannot move the arm or change any setting.

**Healthy result:** IDs 1–6 respond, `model=777` (STS3215), voltage
11.5–12.6 V with under ~1 V spread across the chain.

**If a servo is missing:** usually a daisy-chain connector working loose —
`shoulder_lift` (ID 2) takes the most stress. Power down, reseat every
connector, retry. Do not repeat the scan hoping for a different answer.

**If nothing responds at all:** the 12 V supply is the first suspect. USB
alone does not power the servos, and an unpowered bus scans as complete
silence.

## Stage 3 — Calibrate this arm (~20 min, the arm moves)

Every unit's encoder zero sits wherever it landed at assembly, so the previous
arm's calibration does not transfer.

```powershell
D:\robotics\so101-digital-twin\.venv\Scripts\lerobot-calibrate.exe --robot.type=so101_follower --robot.port=COM8 --robot.id=twin_follower
```

`--robot.id=twin_follower` keeps this separate from the VR project's
`left_follower`, so neither overwrites the other.

**Sequence:**

1. If a calibration already exists you are asked whether to reuse it — type
   **`c`** then ENTER to recalibrate.
2. **Torque releases. The arm goes limp.** Have a hand on it before this.
3. Pose every joint mid-range, away from its hard stops → **ENTER**
4. A live `NAME | MIN | POS | MAX` table appears. Move each joint slowly to
   both extremes: `shoulder_pan`, `shoulder_lift`, `elbow_flex`, `wrist_flex`,
   `gripper`. **Squeeze the gripper fully shut as well as opening it.**
   Skip `wrist_roll` — it is hardcoded 0–4095.
5. Check no joint still reads `MIN == MAX` → **ENTER**

A joint with `MIN == MAX` raises `ValueError` and loses the whole run. The
gripper is the one people forget to close.

Saved to
`C:\Users\abbid\.cache\huggingface\lerobot\calibration\robots\so_follower\twin_follower.json`

**I will then check the JSON** for near-zero ranges, inverted limits and
missing joints, and compare each joint's real span against the simulation's
kinematic span — the comparison that tells us how far apart the two arms
actually are.

Calibration leaves torque **enabled**, so the arm will be stiff afterwards.
That is normal.

## Stage 4 — Task 1: characterise the elbow (~90 min, the arm moves)

The main work. I write `so101_joint_characterization.py`; you run it and
reposition the arm between load conditions.

### What it does

Commands **`elbow_flex` only** through a set of trajectories while logging, at
every sample:

`timestamp` · `commanded_deg` · `actual_deg` · `measured_velocity` ·
`load` · `current` · `voltage` · `temperature` · `experiment_id` ·
`load_condition`

Load, current and temperature come from the STS3215's read-only registers
(addresses 60, 69, 63) — `SOFollower.get_observation()` alone does not expose
them, so the script reads the control table directly.

### Timing — measured on this machine today

| | |
|---|---|
| `perf_counter` resolution | **200 ns** |
| 50 Hz busy-wait loop | mean 20.000 ms, **sd 0.58 ms** |
| 100 Hz busy-wait loop | mean 10.000 ms, **sd 0.08 ms** |

Millisecond-scale latency measurement is comfortably within reach. The script
will **record actual elapsed time per sample** rather than assuming a rate —
the serial round-trip to the servo, not the clock, will dominate the sampling
interval.

### Experiments

| # | Trajectory | What it reveals |
|---|---|---|
| 1 | 30° → 35°, 30° → 40°, 30° → 50°, ten repeats each | Latency, rise time, overshoot, steady-state error, repeatability |
| 2 | 30° → 45° → 30° → 45° → 30° | **Backlash, deadband, static friction** — the sharpest test |
| 3 | Ramps: slow / medium / fast | Where the actual position stops keeping up — the real velocity ceiling |
| 4 | Triangle 30° → 60° → 30° → 60° → 30° | Lag and rounding at the reversal peaks |

### Two load conditions

- **A — low load:** arm folded so gravity produces little torque at the elbow
- **B — higher load:** arm extended so the elbow carries the link's weight

The robot's own mass is enough. Do not add weights yet.

**Your hands:** repositioning between A and B, and watching the arm.

## Stage 5 — Analysis (~30 min, no hardware)

Four plots from the logged CSVs:

1. Commanded vs actual position over time
2. Position error `e = q_cmd − q_actual` over time
3. Commanded vs actual velocity
4. **Actual plotted against commanded, forward and reverse separately** — if
   the two curves do not overlap, that gap is measurable hysteresis

Then the five numbers, and a judgement on what actuator model MuJoCo should
use — chosen from data rather than guessed.

## Why keyboard control waits

`keyboard_robot.py` uses a **global** keyboard hook. It receives keystrokes
regardless of which window has focus — which is why control currently works
with the terminal focused while the viewer misbehaves.

In simulation that is a quirk. **With servos connected it means typing in a
browser, an editor or a chat window would move the physical arm.**

Task 1 sidesteps this entirely: it commands positions programmatically, with
no keyboard listener running. So tomorrow needs no fix.

Before M6 the script needs a focus check or an explicit arm/disarm toggle. I
can write and test that in simulation while you work through the earlier
stages — it costs nothing and removes the blocker.

## If something goes wrong

**Servo stops responding mid-run** — a communication dropout, usually a loose
daisy-chain connector. Power down, reseat, restart that experiment.

**A joint buzzes or strains** — pull the 12 V jack. It is commanding past a
mechanical limit; the commanded range needs narrowing.

**Numbers look impossibly clean** — suspect the logging before believing them.
If actual tracks commanded with no lag at all, we are probably reading back
the command rather than the encoder.

**Arm stiff and unmovable** — torque is enabled. Normal after calibration.
Running calibration again releases it, or pull the 12 V jack.
